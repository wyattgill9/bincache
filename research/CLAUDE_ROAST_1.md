# bincache Design Review: An Evidence-Based Assessment (实事求是)

## TL;DR
- **The single most important finding invalidates a load-bearing premise:** the document's claim that `nix copy --to https://bincache` works "with zero client tooling" is only *half* true and dangerously so. Current Nix's `HttpBinaryCacheStore::upsertFile` does issue HTTP `PUT` (confirmed in `src/libstore/http-binary-cache-store.cc`: `req.method = HttpMethod::Put`), so a PUT-accepting server *can* be pushed to by unmodified `nix copy --to http(s)://` — but this path has no auth story, no atomicity/locking (the Nix source itself notes caches are "inherently racy since there is no locking"), no dedup, and no managed signing. Every major service (Attic, Cachix) ships a bespoke push client precisely because plain-HTTP push is inadequate for real workloads. Design around S3 or a real push protocol, not "PUT just works."
- **Most of the exotic performance work is premature optimization for the wrong bottleneck.** Independent evidence shows client-side `nix build` wall-clock is dominated by single-threaded **xz decompression CPU** and by **serialized narinfo round-trips across a closure**, not by server-side per-narinfo lookup compute. io_uring + kTLS + perfect hashing + rkyv mmap will not move the needle a real user feels until you first get compression and request concurrency right. Build the boring walking skeleton first and benchmark against harmonia/nix-serve-ng/nginx before touching any of it.
- **The Rust ecosystem claims are mostly accurate but the risk profile is understated.** compio is real and used by Apache Iggy; glommio really is effectively unmaintained with the Dec 2025 SPSC corruption bug; kTLS+io_uring is a genuine research-grade unknown (one hobbyist blog, zero production users for this exact combo); and io_uring is *blocked by default* in Docker 25.0.0+ and containerd's `RuntimeDefault` seccomp profile and disabled across Google's fleet — a deployment reality that alone may disqualify io_uring for a widely-deployable cache.

## Key Findings

### Area 1 — Nix protocol correctness (highest priority)
1. **HTTP push is possible but not the "free" path the doc implies.** Nix's HTTP binary cache store implements `upsertFile` via HTTP `PUT` (confirmed in `src/libstore/http-binary-cache-store.cc`: `req.method = HttpMethod::Put`). So `nix copy --to https://server` against a server that accepts PUT of `nar/*.nar` and `*.narinfo` *does* work with stock Nix. **However:** the HTTP store has no authentication beyond netrc/basic, no locking (the source explicitly notes "this is inherently racy since there is no locking on binary caches"), no multipart, and reference-validity checks that fire on upload (`cannot add '%s' to the binary cache because the reference '%s' is not valid`). This is why Attic and Cachix ship dedicated clients (deduplication, chunking, managed server-side signing, auth tokens). The correct architectural decision is to support the **S3 API** (what cache.nixos.org, niks3, and most serious deployments use) and/or a real push path, and treat plain-HTTP PUT as a convenience, not the backbone.
2. **Required read surface (mandatory):** `GET /nix-cache-info` (fields `StoreDir`, `WantMassQuery`, `Priority`); `GET/HEAD /<hash>.narinfo`; `GET /nar/<...>.nar[.xz|.zst]`. Everything else is optional: `.ls` file listings (nix-index/`nix store cat`), `log/<drv>` build logs, `debuginfo/` + `.debug` for separate debug info, `realisations/<drvOutput>.doi` for content-addressed derivations. Harmonia implements ranges, `.ls`, and build-log streaming; you do not need them for a v1.
3. **narinfo fields:** `StorePath`, `URL`, `Compression`, `FileHash`, `FileSize`, `NarHash`, `NarSize`, `References`, `Deriver`, `Sig`, `CA` (content-addressed), and the deprecated `System`. `NarHash` and `NarSize` are required by Nix; `FileHash`/`FileSize` describe the compressed file. Content-Type is `text/x-nix-narinfo`; NAR is `application/x-nix-nar`. A real narinfo body is ~1 KB — Farid Zakaria's "A Nix Binary Cache Specification" shows a curl of the `ruby-2.7.3` narinfo returning `content-type: text/x-nix-narinfo ... content-length: 1058`, `Compression: xz`.
4. **Signing:** `Sig` line format is `<key-name>:<base64 ed25519 sig>`. The signed fingerprint is computed over StorePath + NarHash + NarSize + sorted References (the standard "fingerprintPath" string). Multiple `Sig` lines are allowed and clients accept a path if *any* signature matches a key in `trusted-public-keys`. Key rotation = add the new public key to clients' `trusted-public-keys` before switching the signing key; clients that trust either key see no interruption. Attic does managed server-side signing (the pusher never holds the key); this is a good model to copy.
5. **Client HTTP behaviour that matters:** Nix uses `HEAD`/`GET` for narinfo existence probes; concurrency is governed by `http-connections` (default 25) and the store-side query thread pool. **narinfo-cache-positive-ttl defaults to 30 days (2592000s); negative-ttl defaults to 3600s** — both stored in a client-side SQLite disk cache, and there is also an in-memory `pathInfoCache` that does not respect the negative TTL within a session (issue #3398). Range requests are used for resumption (Harmonia notes transparent zstd is "incompatible with resuming"). Nix relies on the narinfo **`Compression` field**, not HTTP `Content-Encoding`, to decide how to decompress the NAR.
6. **Compression:** Nix supports `xz`, `bzip2`, `zstd`, `gzip`, `br`, and `none` for NARs. zstd support landed in Nix ≥ 2.4 (April 2021) and was partially backported. **Caveat the doc must respect:** older clients (pre-2.4) and some Lix/older deployments in the wild may not support zstd; `xz` remains the safe universal default and is still what cache.nixos.org predominantly serves. This is the crux of the real bottleneck (see Area 2).

### Area 2 — Prior art and the real bottleneck
7. **This is the finding that should reshape the whole project.** Where does substitution time actually go?
   - **Server-side**, narinfo is the highest-frequency request. Gabriella Gonzalez (nix-serve-ng author) wrote "NAR info lookups typically dominate a Nix cache's performance … the majority of a Nix cache's time is spent addressing failed cache lookups" — but this is explicitly a *server-side, informal* claim, and her own benchmarks show narinfo serving is only ~1.5–1.8× improvable by a rewrite, versus ~30× for NAR fetching (by avoiding subprocess spawn).
   - **Client wall-clock** is dominated by (a) **single-threaded xz/LZMA decompression** — a gdb backtrace by user nh2 (NixOS Discourse, "Switch cache.nixos.org to ZSTD…") showed that "despite only pushing ~12 MB/s, the nix process consumes around 100% CPU (varying between 70% and 130% in htop)," pinned inside `lzma_decode()`; decompression is *not* parallelized client-side (issue #12355 confirms "100% cpu - no parallel decompression"); and (b) **serialized narinfo round-trips** across a large closure — issue #5118 ("Substituter query parallelism is far too low") states "a single-line change can make binary cache querying 50x as fast," with a measured 38s (concurrency 32) → 0.73s (concurrency 1000).
   - zstd decompresses ~10× faster than xz (Arch's switch cited ~1300% decompression speedup for ~0.8% size increase; a Nix-corpus micro-benchmark showed xz-9 decompressing a 969 MiB set in ~10s vs zstd-19 in ~1s, at ~23% larger size).
   - **Implication:** a read-optimized cache helps end users most by (1) serving zstd (or offering it) to cut client decompression, and (2) supporting HTTP/2 + keep-alive so clients can pipeline narinfo requests with low RTT — NOT by shaving microseconds off per-narinfo server compute via perfect hashing and mmap. The document is optimizing the wrong layer.
8. **cache.nixos.org scale (real figures):** >1 billion objects and ~600 TB (numtide/narwal, 2024); by Week 32 of 2025, hexa (via blog.erethon.com "This Week in NixOS") reported "the cache is currently 705 Terabytes and growing at a rate of ~280 GB per day. About 100 of those TB are in S3 Infrequent Access storage class." Backend is AWS S3 fronted by the Fastly CDN. This matters for the "all metadata in RAM" idea below.
9. **Prior art to benchmark against:** Harmonia (Rust, nix-community, actix/hyper; recently added direct-SQLite reads dropping narinfo latency ~49% from 158µs→82µs, and zero-copy NAR streaming ~3.2 GiB/s peak); nix-serve-ng (Haskell, binds libnix, ~30× NAR fetch speedup vs nix-serve); Attic (Rust, S3-backed, chunked dedup, server-side signing, LRU GC); ncps (pull-through); niks3 (S3 + GC). None of them use io_uring/kTLS/perfect-hashing; harmonia's numbers (82µs narinfo, multi-GiB/s NAR) are already faster than any real client can consume.

### Area 3 — Rust ecosystem fact-check (mid-2026)
10. **compio:** real, actively maintained (patches merged within hours per Iggy), thread-per-core, IOCP/io_uring/polling, driver decoupled from executor. Confirmed by Iggy as their choice over monoio for "broader io_uring feature coverage." **Confirmed weakness the doc should note:** compio *boxes* every I/O request (heap alloc per op); Iggy found mimalloc's small-alloc pool neutralizes it, and the compio authors declined a slab allocator. compio's own docs warn `send_zerocopy` "is not always faster than send — profile your use case." So the doc's zero-copy assumptions need measurement.
11. **Iggy claims all check out:** migrated Tokio→compio in v0.6.0 (Dec 2025); ">5000 MB/s (5M 1KB msg/s)"; WebSocket P9999 ~9.48ms with fsync-per-message; explicitly hit the mimalloc/boxing and "RefCell across .await" issues. Sources: iggy.apache.org blogs (Feb 2026, Nov 2025).
12. **glommio:** the doc is correct — effectively unmaintained, and issue #700/#701 "Memory corruption in glommio::channels::spsc_queue under concurrent use" (opened Dec 10, 2025) is real, with a fix PR removing public `Clone` from spsc_queue. Do not use glommio.
13. **monoio:** maintained by ByteDance, narrower io_uring coverage than compio, slab-based (avoids boxing). **tokio-uring:** effectively stalled — no meaningful releases in years, changelog untouched since 2022. tokio core remains poll/epoll-based; native io_uring in tokio is not shipping. compio or monoio are the only serious completion-based choices.
14. **kTLS + io_uring — the document's flagged unknown is genuinely unknown.** kTLS (Linux 4.17+) offloads the TLS record layer to the kernel; the `ktls` crate (now under the rustls org, by Amos Wenger/Joe Birr-Pixton) configures it from a rustls handshake. sendfile/splice *can* work on kTLS sockets (nginx `ssl_sendfile on`), and io_uring `send_zc` with kTLS is documented as possible. **BUT** the only demonstration of the full io_uring+kTLS+Rust "zero-syscall HTTPS" stack is a single April 2025 hobbyist blog (habets.se) that required upstreaming two PRs to the ktls crate, did no benchmarks, and warns the code "needs a lot of work." Known limitations: TLS 1.3 key updates and renegotiation are the classic kTLS footguns; NIC hardware offload availability is spotty; the handshake still must be userspace. **Verdict: treat as research, not a v1 feature.** For large-file serving, kTLS+sendfile's win over userspace TLS is real (avoids CPU touching every byte) but only materializes when TLS terminates *in your process* — which a CDN in front makes irrelevant (see Area 4).
15. **io_uring security/deployment posture is getting *worse*, not better, and this is a real threat to the whole approach.** Docker 25.0.0+ (moby PR #46762, "seccomp: block io_uring_* syscalls in default profile") and containerd's `RuntimeDefault` seccomp profile (PR #9320) **block `io_uring_setup/enter/register` by default**; Kubernetes inherits this. The real-world consequence is visible in TigerBeetle issue #1995, where a container "fails to start... error: PermissionDenied" with no epoll fallback. Google's June 2023 Security Blog ("Learnings from kCTF VRP's 42 Linux kernel exploits") reported "60% of the submissions exploited the io_uring component of the Linux kernel (we paid out around 1 million USD for io_uring alone)… io_uring vulnerabilities were used in all the submissions which bypassed our mitigations," and Google subsequently disabled io_uring across ChromeOS, Android (seccomp), and all production servers, and is disabling it in GKE Autopilot. Practical consequence: **a bincache shipped as a container will fail to start or silently lose io_uring unless the operator adds a custom seccomp profile.** compio falls back to polling, but then the entire io_uring rationale evaporates. This alone argues for an epoll/poll-based first version.
16. **Hashers:** claim holds. foldhash is hashbrown's default because it balances quality/speed; rapidhash's geometric-mean rank score (~4.25) and "fastest to pass all quality tests" are from its own benches; gxhash is faster but needs AES/`target-cpu=native` (non-portable). The "hasher dominates the table, 2–5× swing" is directionally right (fxhash's pathological 1.77ns→67.72ns collision blowup on M2 illustrates it). But for a cache keyed on already-uniform 32-byte nix hashes, hasher choice is nearly irrelevant — the input is already a hash.
17. **Perfect hashing:** ptr_hash (PtrHash, Ragnar Groot Koerkamp, SEA 2025, DOI 10.4230/LIPIcs.SEA.2025.21) is the state of the art: **2.4 bits/key**, builds an MPHF for 10^9 keys in ~30s on 6 threads. Confirmed it's an *MPHF* (key→index); you supply your own value array. This is a good fit for a static, pre-built index but adds a rebuild step on every cache mutation — a poor fit for a write-accepting cache. The pthash-rs binding and a BDZ `minimal_perfect_hash` crate (~5 bytes/key, ~25ns lookup) are alternatives.
18. **Binary fuse filters:** the doc's numbers are right. xorf's `BinaryFuse8` is ≈9 bits/key, false-positive ≈2^-8 (<0.4%), 3 memory accesses; the paper states the 3-wise filter reaches 9 bits/key = 12.5% over the theoretical floor (the doc's "13% over floor" is essentially correct), 4-wise ≈8.6 bits/key. Good for negative-lookup short-circuiting (which matters given failed lookups dominate server load), but note the client already caches negatives for an hour, so the server-side filter mostly helps under cold-cache stampedes.
19. **rkyv 0.8:** current major version; supports zero-copy access via `access`/`access_unchecked` and mmap. **Correct caveat the doc should internalize:** `access` (validated) costs a full validation pass proportional to archive size (can be slow on a large index), while `access_unchecked` skips it but is `unsafe` and unsound on malformed/torn data. mmap'ing an rkyv index that a writer is concurrently rewriting is unsound w.r.t. torn writes — you need atomic file swap (write-new-then-rename) + remap, not in-place mutation.
20. **mimalloc vs jemalloc vs glibc:** mimalloc is real and effective (Iggy relies on its small-alloc pooling to hide compio's boxing); the specific "5.3× / 13–22% / ~50% RSS" figures are plausible-but-workload-specific benchmark numbers — treat as "often meaningfully faster and lower-RSS than glibc," and verify on your workload. tikv-jemallocator is the maintained jemalloc binding. Either is a safe pick; this is a one-line change, not an architectural risk.
21. **Huge pages:** "2MB pages give 32× TLB coverage" is roughly right (2MiB/4KiB = 512× bytes per TLB entry, and effective TLB reach expands greatly). The operational advice is sound: THP=madvise or explicit `MAP_HUGETLB` needs `vm.nr_hugepages` reserved (fragmentation makes late reservation fail); Iggy's own tuning uses `vm.nr_hugepages=2048` + `MIMALLOC_RESERVE_HUGE_OS_PAGES`. This is real but pure late-stage tuning — not a design concern.
22. **crossbeam-epoch / seize / arc-swap:** the doc's RCU/snapshot-swap pattern (single writer, many readers, whole-index swap) is a textbook **arc-swap** use case. arc-swap is dramatically simpler than epoch-based reclamation and is almost certainly sufficient; crossbeam-epoch/seize are warranted only if you need fine-grained concurrent structure mutation, which the "swap the whole pre-rendered snapshot" design explicitly avoids. Recommend arc-swap; treat epoch reclamation as unnecessary complexity.
23. **Other crates:** rustix, socket2, rtrb, bumpalo, bitcode, snafu, proptest, bolero, divan, criterion, iai-callgrind, cargo-nextest, cargo-deny, cargo-pgo, nutype, tracing are all maintained and reasonable in 2026. Minor notes: `snafu` vs `thiserror`+`anyhow` is a taste call (thiserror is more common); divan is newer/less mature than criterion (fine to use both); bitcode is fast but its format is not stable across versions (don't use it for the on-disk index — use rkyv for that).
24. **Deterministic simulation testing:** madsim, turmoil, shuttle, loom exist and work, but each targets a slice (loom = concurrency permutations; shuttle = randomized concurrency; madsim/turmoil = network/time simulation, tokio-oriented). **The document's "DST as the centerpiece" is a schedule risk for a solo/small project.** Iggy's own engineers noted that with async Rust "it is very difficult, if not borderline impossible, to achieve total determinism" because you cannot easily replace the executor's time wheel/scheduler — and compio is *not* today pluggable enough to intercept those sources. Layering true DST onto compio would be substantial original R&D. Recommend: use loom for the lock-free bits, proptest/bolero for parsers, and defer full DST.

### Area 4 — Architecture sanity checks
25. **Thread-per-core + SO_REUSEPORT for a read-mostly file server:** SO_REUSEPORT hashes *connections* to shards at accept time; it does not rebalance. With long-lived keep-alive connections and large streaming NAR responses, this causes documented load imbalance — a few heavy connections (a CI machine pulling a huge closure) pin to one shard while others idle; incast and uneven distribution are known pathologies. Mitigations exist (eBPF reuseport socket selection, connection draining) but add complexity. For a cache whose responses are large and long-lived, a shared-accept + work-stealing model (or just letting a CDN/L4 LB spread load) is often *better* than naive thread-per-core.
26. **"All metadata in RAM as pre-rendered response buffers":** do the arithmetic. A narinfo is ~1 KB (cache.nixos.org's ruby example: 1058 bytes). Pre-rendered with HTTP headers, call it ~1.5–2 KB. At 1M paths that's ~1.5–2 GB — fine. At 20M paths, ~30–40 GB — expensive but possible on a big box. **But** cache.nixos.org has >1 billion objects; "all metadata in RAM" does not scale to that class at all, and even a mid-size private cache that never GCs will blow past comfortable RAM. The idea is affordable only for bounded, aggressively-GC'd caches (<~5–10M paths). State the path-count ceiling explicitly.
27. **Pre-rendered *whole responses* (headers included) break per-request variation.** You cannot bake a full response and still correctly support: HTTP/1.1 vs HTTP/2 (different framing), Range requests (partial content, 206, Content-Range), conditional requests (If-None-Match/ETag → 304), Content-Encoding negotiation, keep-alive vs close, and CORS. Pre-rendering the **narinfo body** is fine (it's static text); pre-rendering the **response including headers** is a trap. Restrict the optimization to the body blob and let the HTTP layer add headers.
28. **Rejecting an embedded DB — the doc overstates the case.** SQLite/redb/LMDB/fjall with the OS page cache doing the heavy lifting is what harmonia actually does — and harmonia hit **82µs narinfo latency reading straight from SQLite**, faster than any client needs. An embedded KV store gives you crash-safe writes, atomic updates, and range scans for a few tens of microseconds, and removes the entire "rebuild the perfect-hash index on every mutation," "mmap torn-write soundness," and "custom on-disk format" problem class. For anything that accepts writes, an embedded DB is the *simpler and adequate* choice; the pure-mmap-perfect-hash design only pays off for a truly read-only, rebuild-offline corpus.
29. **In-process TLS + zero-copy vs a CDN/reverse proxy — this undercuts the whole payload-plane design.** cache.nixos.org itself is S3 + Fastly; the standard, proven deployment is to put nginx/Caddy/HAProxy or a CDN in front. Once a CDN terminates TLS and caches NARs at the edge, in-process kTLS/sendfile/io_uring zero-copy buys **almost nothing** — the origin serves cache-misses only, and the CDN handles the fan-out. The zero-copy payload plane is justified *only* for a self-hosted, CDN-less, TLS-terminating origin under heavy direct load — a narrow niche. Quantify honestly: for most deployments the answer is "put Caddy in front and serve plain files."
30. **Closure-aware GC:** Attic does content-addressed dedup with LRU garbage collection; niks3 and narwal exist specifically because GC'ing a Nix cache correctly (never delete a NAR still referenced by a live closure) is hard. Known pitfalls: races between GC and concurrent pushes, reference-counting across the closure graph, and S3 eventual consistency. This is a genuinely hard sub-problem the doc should scope explicitly rather than hand-wave.

## Details

### What the document gets right (confirm briefly)
- compio is the correct completion-based runtime choice; glommio is correctly rejected; the glommio SPSC bug is real (Dec 2025, issue #700/#701).
- Binary fuse filter numbers (~9 bits/key, ~13% over floor, 3 accesses) are accurate.
- ptr_hash/PtrHash at 2.4 bits/key is real and best-in-class.
- rapidhash/foldhash characterization is accurate.
- mimalloc's value for compio's per-op boxing is real (Iggy confirms).
- The kTLS+io_uring interaction being flagged as an unknown is exactly right — it *is* an unknown.
- Huge-page and THP guidance is directionally correct.

### What the document gets wrong or overstates
- **"`nix copy --to` works against bincache with zero client tooling":** overstated. PUT works mechanically but lacks auth, atomicity, dedup, and server-side signing; real services all ship push clients. Plan for S3 and/or a real push protocol.
- **Optimizing server-side narinfo lookup latency as the headline goal:** mistargeted. Harmonia already does 82µs; the client bottleneck is xz decompression and narinfo *round-trip concurrency*, not server compute.
- **Zero-copy payload plane (kTLS/sendfile/io_uring send_zc) as core:** mostly irrelevant behind a CDN, which is the standard deployment; and blocked by container seccomp defaults.
- **DST as centerpiece:** not realistically achievable on compio today; schedule risk.
- **Pre-rendered full responses:** breaks HTTP/2, ranges, conditional requests, content negotiation.
- **Rejecting embedded DBs wholesale:** an embedded KV store is simpler and fast enough for the write path.

### Pre-coding checklist synthesis (Area 5)

**Blocking unknowns → cheap spikes:**
- *Does io_uring even run in the target deployment?* Spike: run a trivial compio program in your target container/orchestrator with default seccomp. ~1 day. Resolves whether io_uring is viable at all.
- *Is decompression or metadata the client bottleneck for your corpus?* Spike: profile `nix build` of a large closure against harmonia serving xz vs zstd. ~2 days. Resolves whether the whole optimization thesis holds.
- *Does `nix copy --to https://` round-trip cleanly against a minimal PUT server?* Spike: 50-line axum server accepting PUT + serving GET; test push/pull with stock Nix and Lix. ~1–2 days. Resolves the compatibility premise.
- *kTLS+io_uring viability:* Spike: reproduce habets.se's stack with current ktls/rustls; measure vs userspace rustls for a 100 MB NAR. ~1 week. Resolves whether the payload plane is worth pursuing at all (likely: no, behind a CDN).

**Decisions that must be made before coding (hardest to change later):**
- Push protocol: plain HTTP PUT vs S3 API vs custom (pick S3-compatible for interop).
- Default NAR compression served: xz (universal) vs zstd (fast) vs both/negotiated.
- Write model: read-only rebuildable corpus vs mutable cache (determines DB-vs-perfect-hash).
- Signing model: client-side vs managed server-side (Attic-style).
- Deployment stance: CDN-fronted (drop zero-copy) vs standalone origin.
- GC/retention policy and its correctness model.

**Baselines to measure first:** harmonia, nix-serve-ng, and plain nginx serving a static NAR tree; end-to-end `nix build` wall-clock over LAN and simulated WAN, broken into narinfo-resolution / NAR-download / decompression / local-insertion.

**Recommended walking skeleton:** plain files + SQLite/redb index + axum/hyper on tokio (no io_uring), TLS via Caddy in front, implementing `/nix-cache-info`, `GET/HEAD narinfo`, `GET nar`, ed25519 signing, and PUT/S3 write — serving xz by default. Layer exotic optimizations only after Stage 0 proves each one necessary.

## Recommendations

### Stage 0 — Measure before building (1–2 weeks)
1. Stand up **harmonia, nix-serve-ng, and plain nginx serving a static NAR tree** against a real store. Measure end-to-end `nix build`/`nix copy --from` wall-clock for a large closure (e.g. a full NixOS system) over LAN and over a simulated WAN. Break down narinfo-resolution vs NAR-download vs decompression vs local-insertion time (use `nix --debug`, `perf`, and process CPU sampling as nh2 did).
2. **Decision gate:** if harmonia/nginx already saturate the client (they almost certainly will — 82µs narinfo, multi-GiB/s NAR), the ambitious design is *not necessary* and you should scope bincache to a specific unmet need (GC, multi-tenancy, a corpus too large for harmonia's SQLite, or per-request signing at scale).

### Stage 1 — Walking skeleton (usable with real Nix clients)
3. Build: **plain files on disk + a simple index (SQLite or redb) + axum/hyper on tokio, no io_uring, TLS via rustls or (better) terminated by Caddy in front.** Implement exactly: `/nix-cache-info`, `GET/HEAD /<hash>.narinfo`, `GET /nar/...`, ed25519 signing with correct fingerprint, and `PUT` acceptance (or S3 backend) for the write path. Serve **xz by default, zstd optionally.** Verify against real `nix copy --to`, `nix build`, and `nix path-info --store`.
4. Ship this. It is already competitive with harmonia for most users.

### Stage 2 — Optimize, each gated on a Stage-0 measurement
5. Add **HTTP/2 + keep-alive tuning** and confirm client narinfo concurrency improves (highest-value real win).
6. Add **zstd serving** and measure client decompression improvement (second highest-value win).
7. Only if profiling shows the metadata plane is actually hot: add in-RAM pre-rendered **narinfo bodies** (not full responses) behind arc-swap; add the binary-fuse negative filter for stampede protection.
8. Only if you have a bounded, read-mostly, offline-rebuildable corpus: add the ptr_hash mmap index.
9. Treat **io_uring, kTLS, send_zc** as experimental branches behind feature flags, each with a before/after benchmark and an epoll fallback — and only pursue if you have a CDN-less, TLS-terminating, high-direct-load deployment that Stage 0 proved needs it.

### Thresholds that change the plan
- If Stage 0 shows narinfo round-trips (not decompression) dominate → prioritize HTTP/2 + concurrency, deprioritize everything else.
- If target corpus > ~10M paths or unbounded → drop "all metadata in RAM"; commit to an embedded DB + page cache.
- If deployment target is containers/Kubernetes → drop io_uring (seccomp blocks it); use tokio/epoll.
- If a CDN is in the picture → drop the zero-copy payload plane entirely.

## Caveats
- **Compression status of cache.nixos.org is in flux/unconfirmed:** it remains predominantly xz as of the sources reviewed; a full default switch to zstd was debated (nixpkgs PR #376365) and partially adopted by Cachix (1.1) but there is no confirmation the main Hydra pipeline flipped its default. Verify current state before hard-coding assumptions.
- **No published client-side benchmark isolates SQLite/fsync store-insertion cost** as a fraction of `nix build` time; the "decompression + network dominate" conclusion rests on nh2's gdb evidence and issues #12355/#5118, which are strong but not a formal study.
- **Several performance figures in the document (mimalloc 5.3×/13–22%/50% RSS, and any throughput numbers) are workload-specific vendor/benchmark claims** — directionally plausible, but must be re-measured on the NAR-serving workload, not accepted as-is.
- **Gonzalez's "narinfo lookups dominate" is self-described as informal server-side experience,** not a controlled measurement; her own table shows only ~1.6–1.8× narinfo improvement headroom.
- **io_uring+kTLS production evidence is essentially one hobbyist blog** (habets.se, April 2025) with no benchmarks; treat any performance claim for that stack as unproven.
- Nix protocol details were verified against current `NixOS/nix` master source and the 2.x reference manuals; Lix may differ in minor behaviours and should be tested separately if it's a target client.
